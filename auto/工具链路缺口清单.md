## 二、A3 实现路径（重点节）

### 2.1 判定工具移植：旧分支 grab_check 六要素

旧分支 auto/task/grab_check.py 已把 §4.3 的判定要素做成**单要素接口**
（每条规则一个独立函数、组合逻辑留给上层、返回三态、全参数化）：

| 旧函数 | 判定 | 旧参数（common config） |
|--------|------|------------------------|
| check_stretch_in_range | 伸缩舵机1/2 均在伸缩运动范围（共用一套） | grab_stretch_range_min/max |
| check_stretch_aligned | 两伸缩舵机偏差 ≤ 容差（机构无卡斜） | grab_stretch_deviation_tol |
| check_stretch_in_hold | 伸缩机构处于静止保持位范围 | grab_stretch_hold_range_min/max |
| check_grab_engaged | 抓取舵机已离开静止范围（= 执行了夹取） | grab_idle_range_min/max |
| check_grab_in_target_range | 抓取舵机落在魔方/球夹取范围（分开配） | grab_cube/ball_range_min/max |
| is_grabber_idle | 抓取舵机在静止范围（调度用） | grab_idle_range_min/max |

移植方案：适配进 **auto/actuator**（新分支 ActuatorState 已带
stretch_servo_1 / stretch_servo_2 / grab_servo 字段，数据入口现成）；
参数从 common config 挪到 **auto/params.py 新增 actuator 段**（占位 =
舵机全行程 0~4095，现场标定后填，方便调试随时改）。

### 2.2 脱落判定实现路径（你的思路整理）

- **数据链（收侧已就绪）**：舵机角度的底层回读由 STM32 负责 → 角度随
  0x02 状态帧经串口回传 → actuator 接收线程入 RuntimeData
  （actuator_queue + actuator_state 最新镜像）→ 判定工具取最新角度做
  范围判定。我们这边只做串口接收（已完成），不碰底层。
- **核心逻辑（口述整理）**：
  1. 抓取时下发的**指令角必然小于夹住物品后的保持角**——爪瓣被物品挡
     住，舵机到不了指令角，停在指令角上方的"夹取范围"里；
  2. 物品脱落后爪瓣失去阻力，舵机继续向指令角闭合，**实际角度从夹取
     范围直接回落到指令角**（≈ 空爪闭合位）；
  3. 判定 = 监视抓取舵机角度：**离开对应夹取范围、落回指令角附近并
     稳定**若干采样周期 → 判脱落。
- **与旧分支的关系**：旧 drop_check 只做"可投判定"（judge_cube/ball_
  droppable），脱落判定是新做的；"稳定"去抖复用 §1.2 连续 N 次稳定的
  思路。负载 / 电流回读（§6.6 思路 B）作为可选辅助——舵机型号支持就
  加，不做也不影响主路径。

**待讨论 / 待实测（供拍板）**：

1. **指令角从哪来**：每次抓取的指令角若固定，直接把"空爪闭合位范围"
   标定成参数（最简单，推荐）；若每次指令角不同，flow 发指令时记录
   下来作参照。二选一，现场定。
2. **区分度**：夹取范围下界与指令角之间要留出间隔，否则"夹得松"和
   "已脱落"分不开——即伪代码 §6.6 待确认 2（空爪闭合位 vs 夹球/夹魔方
   角度的区分度）。
3. **去抖窗口**：判"稳定"要几个采样周期，防途中抖动误判；需实测确认
   飞行震动会不会让爪瓣向闭合位滑动（脱落判定的方向是"往指令角闭合"，
   震动一般只造成短暂偏移、理论上不会误触发，待验证）。
4. **回读频率**：要能支撑时刻监视（脱落发生到判定的延迟），联调时看
   0x02 实际频率（D 类）。

### 2.3 G2 机构健康监视（你的思路记录）

- 职责划分：**伸缩舵机判机构健康**——不在运动范围 / 偏差超容差 / 不在
  保持位 → 机构可能出问题、可能坏了；大部分时间机构正常，**在正常的
  基础上才用抓取舵机判抓取**。
- 实现形态（你定的方向）：**状态机 + 线程监视舵机状况**，代码在 flow
  阶段做（现成的监视线程模式可参考：landing-imu）。

## 三、B 类拍板记录

### B2 / B3 颜色→桶映射（同一件事，做补丁）

- **时机**：第一次投放（魔方）完成之后做一次，映射建立后一直有效
  （§6.7 例外任务）。
- **方案（口述整理）**：
  1. 一个**六元素列表**，列表顺序对应桶的顺序 / 位置；
  2. YOLO 识别定位各桶 → 色块识别（color_blob 六色工具）读桶底颜色；
  3. 按顺序把颜色标签放进列表对应位置 → 得到"桶序 → 颜色"映射。
- **球的投放规则（补充点）**：球要投进**对应颜色**的桶——球投放时按
  "球颜色 → 列表 → 桶"选投放目标。
- **与框架关系**：不冲突，多一个处理模式——flow 写流程时加判断与分支
  （流程树加节点）；映射的存放位置（RuntimeData / 计数装置）随 flow 定。
- pan/bucket 识别结果存放（B3）与此同源：投放阶段抽帧即用即取，
  不另设缓存。

### B4 人工提示渠道（后面单独做补丁模块）

- PC 上做处理 → GUI 直接显示；树莓派等运算平台 → 换其他提示方式
  （蜂鸣器等）。具体方案后面讨论；flow 骨架先留统一提示函数占位。

### B5 帧采集（不缺）

- common/hardware 的图像数据接口（CameraManager.read_frame）直接拿来
  用；自动链路自己取帧、自己抽帧推理，不需要额外的采集端设计。

### B1 FlowCounter（flow 阶段做）

- 就是任务计数 / 调度用；加减发生在整个流程里（投放完成 N+1、掉落计入
  消耗、ball_done ≥ 6 后全抓魔方等），随 flow 骨架一起定字段与存放。

## 四、C 类拍板记录

1. **C1 密集口径**：密集程度**只用魔方来算**——只有魔方会影响抓取，
   球不参与密集统计。落地影响：score_cubes 的邻域 = 全部魔方（含圈外，
   已是）；score_balls 的邻域现传 all_balls，需改为以魔方列表为准
   （小改动，近期补）。由于球区与魔方区分开，球的"周边魔方数"通常
   为 0，等价于球评分不受密集影响——若你的意思就是"球评分不要密集
   项"，改法相同，不会做错方向。
2. **C2 六色分值**：GUI 得分说明（common/ui/display.py）——"魔→a:10；
   b区: 黄20 绿30 棕40 蓝50 粉60 黑70"。初值 = 分值 ÷ 70 归一化
   （黑=1.0，比例与分值一致），已填入 auto/params.py BALL_COLOR_SCORES；
   权重 / plateau / 密集半径等继续全部 params 可调（原型阶段不调关系，
   参数接口留好随时改）。
3. **C3 / C5~C10**（重飞上限、阶段超时处理、起飞确认方式、不可投循环
   上限、场景三归属、桶底细节、G2/G3 监视形态）：flow 阶段的逻辑书写
   问题，写 flow 时处理，现在不管。
4. **C4 三舵机组合逻辑**：定稿时问你；你的思路已记录（§2.3）——伸缩
   舵机判机构健康 → 正常基础上用抓取舵机判抓取；组合代码在 flow 写，
   机构健康做成状态机 + 线程监视。
