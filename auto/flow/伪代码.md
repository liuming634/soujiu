# auto/flow 伪代码（逐阶段补充，只做伪代码与技术路线，不含实现）

> 总框架（已定，所有阶段共用）：
>
> - **单次完整流程做好 → 外层循环反复执行**；不搞一次性复杂编排。
> - **计数装置**贯穿全程：记录流程走到哪、完成了几轮/抓了几个投了几个，
>   参与决定循环走向。
> - **每个阶段内部是树状分支处理**：多种状况各走各的路，分支后还会
>   回跳前面的节点重新走（往复执行），不是顺序跑完就结束。
> - **阶段时间周期**：每个阶段有自己的执行时间窗口（config 化），超时
>   走该阶段的超时分支——避免阶段间执行顺序问题、相互影响。
> - **角色分工（重要）**：无人机由**人工飞行**，本代码只做**抓取机构
>   的自动化**——识别、判定、给下位机发指令、切换状态机；"是否重新
>   飞"由人工决定，起飞/转场/落点均由人工完成。
> - **项目定位**：比赛已结束，本框架用于开源与技术沉淀——追求链路
>   完整、思路清晰，不做替代人工的完全鲁棒自动化。
>
> 约定：AI 按队伍口述落笔，不自行设计流程。本文件不含可运行代码；
> 伪代码定稿后，按各模块 `__init__.py` 写明的职责拆分实现。
> **维护规则：每新增一个阶段，先在下方流程树里挂节点与回边，再追加
> 对应小节；任何走向改动，树与小节两处同步改。**

## 流程树（总览 · 随阶段更新）

```
自动流程（根）
│   计数装置挂在根上：current_stage / 各阶段通过状态 / 抓投计数
│   （每轮更新，参与决定走向与终止，字段随阶段补充，见 §1.7）
│   每阶段自带执行时间周期（config），超时走该阶段超时分支
│   全局监视贯穿：机构异常监视（§7.1）+ 脱落监视 API（§7.2 场景表）
│
├─ 阶段一 降落判定（§1）
│    ├─ 判稳通过（连续 N 次稳定）→ 阶段二（未抓物品；已抓物品 → 投放系列，§5.2-4）
│    ├─ 读数抖动（变化量 > 容差）──↺── 清零重计，本阶段重新采样
│    ├─ 无回传 ──↺── 重试 ≤ 上限 → 超限：人工介入（串口异常）
│    ├─ 总超时仍未稳定 ────────────────────→ 人工介入 / 终止
│    └─ 串口长期失效 ──（可选）──→ 备选路线：图像判稳（§1.5）
│
├─ 阶段二 可抓判定（§2）：本轮该抓品类（计数装置定）是否有目标在抓取圈内
│    ├─ 可抓（本轮品类目标在圈内）──────────────→ 阶段三
│    ├─ 无本轮品类目标 ──→ 重新飞 ⇒ 跳回【阶段一】→ 重新判降落 → 阶段二
│    ├─ 全在圈外 ──→ 重新飞 ⇒ 跳回【阶段一】→ 重新判降落 → 阶段二
│    └─ 识别抖动（各帧结论不一致）──↺── 防抖连看 M 帧，本阶段重识别
│
├─ 阶段三 评分选靶（§3）：评估先抓哪一个
│    ├─ 评分完成，取分数最高者 ─────────────→ 阶段四
│    └─ 并列 → 编号小者优先（稳定排序）
│
├─ 阶段四 抓取执行（§4）：坐标换算发指令，三舵机角度判定成败
│    ├─ 抓取成功 ──────────────────→ 阶段五（人工起飞转场）
│    ├─ 抓取失败 ──→ 跳回【阶段二】重新选靶（N 不变；累计 3 次 →
│    │              切【飞行中】、人工重飞 ⇒ 1A）
│    ├─ 无回传 ──↺── 重试 ≤ 上限 → 超限：人工介入
│    └─ 阶段时间周期超时 ──→ 处理方式待确认（§4.5-4）
│
├─ 阶段五 起飞转场（§5）：抓取成功后人工起飞
│    ├─ 人工起飞，代码切【飞行中】──→ 跳回【阶段一】降落判定
│    │    └─ 判稳通过后按已抓物品标记路由 → 投放系列（阶段六）
│    └─ 长时间未起飞 → 提示人工
│
├─ 阶段六 投放执行（§6）：判定容器可投 → 发指令投放
│    ├─ [盆·魔方] 盆 ROI 与抓取圈重合面积 ≥ 阈值 → 发投放指令
│    ├─ [桶·球] 桶 ROI 中点在抓取圈内 → 发投放指令
│    ├─ 不可投 → 提示人工重新飞 ⇒ 跳回【阶段一】→ 再进阶段六
│    │            （N 不变、已抓标记保持）
│    └─ 投放完成（动作完成 或 判定脱落，§6.6）→ N+1 → 提示人工飞回
│              ⇒ 跳回【阶段一】→ 阶段二（下一轮，品类切换）
│
├─ 阶段七 …（待队伍定义，定义后挂到这里）
└─ （后续阶段逐个挂到这里；跨阶段回边统一写成 ⇒ 跳回【阶段X】）
```

- 图例：`──→` 正常推进；`↺` 本阶段内回跳（自环）；
  `⇒ 跳回【阶段X】` 跨阶段回边（往复执行）；`(待定义)` 占位节点。
- 执行主体：所有"重新飞 / 起飞 / 飞回"均由**人工操作飞机**完成；
  代码只负责切状态机、给下位机发指令、读回传并判定。
- 树里只画"节点 + 分支去向"，处理细节一律看对应小节；走向有变时
  树与小节同步改。

## 状态机与计数工具（总框架：阶段跑在状态里）

三个运行状态（粗粒度），各阶段（细粒度流程）在状态里执行。飞机由
**人工飞行**：代码只切状态、发指令、读回传判定；起飞/转场/落点由
人工完成：

- 飞行中 →（判稳通过，未抓物品）→ 抓取态（阶段二/三/四 抓取系列）
- 抓取态 →（不可抓：提示人工重新飞，N 不变）→ 飞行中
- 抓取态 →（抓取成功 → 阶段五：人工起飞，代码切飞行中）→ 飞行中
- 飞行中 →（判稳通过，已抓物品）→ 投放态（阶段六 投放执行）
- 投放态 →（投放完成 = 动作执行完成 **或** 判定物品脱落；N+1、
  已抓标记清空）→ 提示人工飞回抓取区 → 飞行中 →（判稳通过，
  未抓物品）→ 抓取态（下一轮，品类随 N 切换）
- 任意状态 →（人工终止）→ 结束
- **飞行中**：未降落 / 人工起飞转场途中；阶段一在此状态下判稳。
- **抓取态**：降落停稳且未抓物品，准备并执行抓取的一系列动作；
  阶段二（可抓判定）→ 阶段三（评分选靶）→ 阶段四（抓取执行）。
- **投放态**：降落停稳且已抓物品，准备并执行投放的一系列动作；
  阶段六（投放执行）。

计数工具（FlowCounter，贯穿全程）：

- 核心字段：**抓取任务计数 N**（当前是第几次抓取任务）。映射规则
  **已定**：第 1 次抓魔方，之后魔方/球**交替**（奇数 → 魔方、
  偶数 → 球）；场上数量：魔方 15 个、球 6 个。
- **投放完成定义（已定）**：投放动作执行完成 **或** 舵机角度变化
  判定物品脱落——两者都算本轮投放完成，N+1 进入下一轮，必须切换
  到下一个品类的抓取。
- **品类消耗计数（已定）**：cube_done / ball_done，投放完成时对应
  +1；**掉落也计入消耗**（球只有 6 颗，掉落丢了的不再等——重抓同
  品类时那颗若还能被识别到仍可能被抓回，丢失则已计数、流程不卡）。
- 另记录：**已抓物品标记**（无/魔方/球，判稳通过后路由到抓取态还是
  投放态，见 §5.2-4）、各阶段通过状态、当前状态。
- N 只在"投放完成、进入下一轮"时 +1；重新飞不算新任务，N 不变。
- **任务完成条件（已定）**：按交替顺序执行；**ball_done ≥ 6 → 后续
  轮次全部抓魔方**（不再交替）；**cube_done ≥ 15 → 任务完成**（G1
  汇总收尾）。

## 阶段一：降落判定（是否已降落、准备抓取）

### 1.1 职责与出入参

- 职责：判定飞行器已降落稳定、进入可抓取状态；通过后流程推进到阶段二。
- 输入：下位机回传数据 ActuatorState（主路线）／相机连续帧（备选路线）。
- 输出（三态，沿用项目约定）：
  - `True`  = 已判定降落稳定，准备抓取
  - `False` = 未降落／稳定超时
  - `None`  = 数据缺失（无回传／无帧），无法判定
- 通过后的动作：计数装置记录（见 1.7）；进入抓取系列（未抓物品 →
  阶段二）还是投放系列（已抓物品，阶段待定义）由状态机按已抓物品
  标记路由（见 §5.2-4）。

### 1.2 下位机数据判稳（机构侧，与 §1.4 IMU 互为佐证）

思路：actuator 回传的电机/舵机读数在空中（机体震动 + 机构微调）会持续
抖动，降落后趋于静止；**连续若干个采样周期读数几乎不变 → 判定已降落**。
（空中/落地的读数差异特征待实测标定，先用"变化量 ≤ 容差"的通用判稳。）

```
function 阶段一_降落判定() -> True | False | None:

    stable_count = 0                          # 连续稳定采样计数
    prev_state   = None                       # 上一次采样
    retry        = 0

    loop (总超时未到):
        state = actuator.read_actuator_state()      # 拉模式读一次回传

        if state is None:                           # 分支：无回传
            retry += 1
            if retry > 重试上限:
                提示人工（串口异常）
                return None
            continue                                # 回跳：重新读

        if prev_state is not None:
            Δ横向 = |state.horizontal_motor - prev_state.horizontal_motor|
            Δ旋转 = |state.rotate_motor    - prev_state.rotate_motor|
            if Δ横向 ≤ 容差 and Δ旋转 ≤ 容差:
                stable_count += 1
            else:
                stable_count = 0                    # 分支：抖动 → 清零重计

            if stable_count ≥ 稳定帧数N:
                计数装置.记录(阶段一通过)
                return True                         # 已降落，准备抓取

        prev_state = state
        sleep(采样间隔)

    return False                                    # 分支：总超时仍未稳定
```

### 1.3 技术实现要点（下位机判稳）

- 数据源：auto/actuator 拉模式读回传（复用 common/hardware/serial_protocol.py，
  与手动模式同协议），只取最新一帧，旧帧覆盖。
- 判稳指标：横向/旋转电机闭环读数的**帧间变化量**（死区容差内视为静止）；
  可扩展把伸缩/夹取舵机（应处于待命保持位）一并纳入判稳。
- 采样节奏：由下位机回传频率决定采样间隔与 N 的取值（待实测）。
- 参数全部进 config：容差 / 稳定帧数N / 采样间隔 / 重试上限 / 总超时。
- 待确认（电控/实测）：
  1. 回传频率多少，决定 N 与采样间隔怎么取；
  2. 空中抖动幅度 vs 落地静止的区分度（容差定多大）；
  3. 是否有更直接的降落信号可用（如下位机自身状态位），有则优先。

### 1.4 落地判定：冲击触发 + 多源短确认（采用方向）

思路：不等"稳定持续很久"，直接**检测落地冲击事件**（实时性优先），
触发后用很短的确认窗做多源并联确认。

**主判据（触发，毫秒级）**：IMU 加速度尖峰——触地瞬间出现远超 1g 的
冲击尖峰（持续几十毫秒），检测到尖峰 = 落地事件。跳变本身很快：
几十毫秒的尖峰、零点几秒内回到 1g 附近——慢的从来不是跳变，而是
"确认它真的稳了"的观察窗，所以把跳变从"要等它过去"变成"主动
检测它"作为触发。

**短确认窗（触发后约 0.5s，多源并联，满足即判停稳）**：

- **IMU**：加速度回到 1g 附近带宽 + 角速度 ≈ 0（冲击已衰减、机体
  静止）
- **图像**：前后帧差 / 光流幅值 < 阈值（画面静止，实现见 §1.5）
- **YOLO 辅助**：识别框位置前后帧基本不动（画面没在动，顺带确认
  目标可见，给阶段二热身）
- **接收机（待定）**：通道值不变（人工已停止操作）——注意判据是
  "通道值不变"而非"没有数据"，接收机一直在发帧；另可取辅助通道
  做**自动模式使能开关**，失控保护触发时通道跳变恰好用于退出自动

确认策略：各源条件满足的条数达到设定值即通过（条数/权重可 config），
不必全部满足——单源失效不卡流程。

- 数据源：飞控 IMU（电控转发或 MAVLink）或独立 IMU（MPU6050/ICM
  系列，I2C 接树莓派），接口一致。
- config 参数：冲击触发阈值（g）/ 确认窗时长 / 帧差阈值 / IMU 静止
  带宽 / 需满足条件数。
- §1.2 下位机回传判稳保留为机构侧佐证（一个看机体、一个看机构）。

### 1.5 图像帧间确认（确认源之一，兼作备用路线）

思路：连续几帧画面几乎无变化 → 画面静止。既是 §1.4 确认窗里的
图像确认源，也可独立为备用判定路线（主源不可用时切换），
flow 只认接口不认实现。

```
function 图像判稳(帧序列) -> True | False | None:
    取连续 K 帧（K ≈ 3~5）
    方案A 光流：
        相邻帧算光流（cv2.calcOpticalFlowPyrLK 稀疏点 / Farneback 稠密）
        平均光流幅值 < 幅值阈值 → 本组判定"静止"
    方案B 帧差：
        相邻帧灰度差分，差分均值 / 变化像素占比 < 阈值 → "静止"
    连续 M 组都静止 → return True
    任一组不静止 → 清零重计（同主路线的树状处理）
    无帧 / 相机断线 → return None
```

- 优点：不依赖下位机，串口异常时可兜底。
- 缺点：光照突变、旋翼投影晃动会误判；悬停微晃与降落的阈值难区分；
  计算开销比读串口大。
- 参数同样 config 化：K / M / 幅值阈值 / 判稳超时。

### 1.6 本阶段分支总表（树状处理预设）

| # | 状况           | 检测点                  | 处理                        | 回跳/去向              |
| - | -------------- | ----------------------- | --------------------------- | ---------------------- |
| 1 | 数据缺失       | IMU/相机/串口 read None | 重试 ≤ 上限，提示人工      | 回跳重读 → 人工       |
| 2 | 落地冲击触发   | 加速度尖峰超阈值        | 进入短确认窗（多源并联）   | → 确认判定            |
| 3 | 确认通过       | 确认窗内满足条件数达标  | 判定停稳                    | 计数装置记录 → 路由   |
| 4 | 确认未通过     | 窗内条件不满足          | 继续等待下一次触发/确认    | 回跳继续采样           |
| 5 | 触发/确认超时  | 阶段时间周期超限        | return False，提示人工     | 人工介入 / 终止        |
| 6 | 主源失效       | IMU 长期无数据          | （可选）切图像独立判稳 1.5 | 备用路线               |

### 1.7 计数装置（框架占位，随阶段补充细化）

- 一份流程级计数器 FlowCounter，贯穿循环全程：
  当前阶段、各阶段通过状态、抓取成功数、投放数。
- 核心用途：**抓取任务计数 N 决定本轮抓魔方还是球**（详见"状态机与
  计数工具"一节与 §2.1）。
- 阶段一写入：`landing_done = True`（进入阶段二的依据之一）。
- 具体字段与存放位置（是否镜像进 RuntimeData 供 GUI 显示）随后续阶段
  一起定，不提前设计。

## 阶段二：可抓判定（降落位置能否直接抓取）

### 2.1 职责与出入参

- 职责：阶段一确认降落后，判定**本轮该抓的品类**有没有目标落在抓取圈
  内——本轮品类（魔方还是球）由计数装置按抓取任务次数给出（见"状态机
  与计数工具"一节）。只有本轮品类的目标在圈内才算可抓；另一类物品在
  画面里不影响判定。
- 输入：当前帧（YOLO 识别）+ 本轮品类（来自计数装置）。
- 输出：
  - 可抓 = 本轮品类的圈内目标列表（≥1 个，交阶段三评分选靶）
  - 不可抓 + 原因码（`无本轮品类目标` / `全在圈外`，供树状走向决策）
  - `None` = 识别不可用（无帧/相机断线），无法判定
- 通过后的动作：计数装置记录本轮品类与目标数 → 阶段三。

### 2.2 情况罗列组合（状态矩阵）

判定"在抓取圈内"的标准：目标 ROI 中点落在抓取圈内（沿用既有约定，
与手动模式画圆公式一致，看到即可抓）。"连续 M 帧"为防抖门槛：
识别有漏检/边缘抖动，单帧结论不算数。

| #  | 本轮品类（计数装置定） | 识别结果（连续 M 帧一致） | 抓取圈内     | 判定               | 走向                         |
| -- | ---------------------- | ------------------------- | ------------ | ------------------ | ---------------------------- |

### 2.3 流程分支（树状；伪代码待流程确认后补）

1. 计数装置给出本轮品类（第几次抓取任务 → 魔方/球，映射规则见 §2.5-1）。
2. 取当前帧 → YOLO 识别（魔方/球/盆/桶一次推理全出），**只取本轮品类
   的目标**。
3. 防抖：连续 M 帧结论一致才认定；不一致 → 回跳 2。
4. 无本轮品类目标 → 原因码=`无本轮品类目标` → 防抖重试确认 → 重新飞 ⇒
   跳回【阶段一】重新判降落 → 阶段二。
5. 有目标 → 按抓取圈过滤（目标 ROI 中点在圈内才算可抓）。
6. 圈内 ≥1 个 → 可抓；计数装置写入本轮品类与目标数 → 阶段三。
7. 全在圈外 → 原因码=`全在圈外` → 防抖重试确认 → 重新飞 ⇒
   跳回【阶段一】重新判降落 → 阶段二（重新飞次数上限见待确认 §2.5-2）。

### 2.4 技术实现要点（大概，后面按此拆模块）

  **本轮品类**（计数装置给出）的目标；盆/桶识别结果照常入库，留给后面
  投放阶段用。
- 推理时机（部署约定）：仅在降落确认后**抽帧推理**，不连续跑模型；

- 抓取圈过滤：region 模块做"ROI 中点是否在圈内"判定（圈内/圈外判定
  方法沿用上一版"对比板查色"思路；抓取圈比例 config 化，与手动模式
  画圆公式一致）。
- 多帧防抖：连续 M 帧结论一致才认定，兜住漏检与边缘置信度抖动。
- 编号：目标 ROI 中点先比 x（左→右）、x 同比 y（上→下），从 1 起
  （沿用既有约定）。
- 参数全部进 config：置信度阈值 / 防抖帧数 M / 重试上限 / 判定超时。
- 涉及模块：detection（识别+编号+入库）、region（圈内过滤）、
  flow（本阶段编排 + 计数装置写入）。

## 阶段三：评分选靶（评估先抓哪一个）

### 3.1 职责与出入参

- 职责：阶段二判定可抓后，对本轮品类的圈内候选目标逐个评分，选出
  **先抓哪一个**（评分框架沿用上一版 scoring 模块的标准，后面重新实现
  或直接搬用）。
- 输入：阶段二输出的可抓目标列表（本轮品类、均在圈内）+ 当前帧。
- 输出：按分数从高到低排序的目标列表（分数最高 = 先抓；并列保持
  稳定顺序，编号小者优先）。
- 通过后的动作：计数装置记录选中目标 → 阶段四（抓取动作，待定义）。

### 3.2 评分标准（从上一版评分模块重写过来）

总分 = 各因子加权求和；权重、半径、六色分值全部 config 化。

- **距离因子**（魔方/球同规则）：目标 ROI 中点到抓取圈圆心的距离；
  plateau 比例 × 半径以内同分 1.0，以外线性递减，到圆边界为 0。
- **颜色因子**（仅球）：球 ROI 内判主色（六色：黑/棕/粉/蓝/黄/绿）→
  查 config 里该颜色球的分值；判不出主色记 0。
- **密集因子**（魔方/球同规则）：以目标 ROI 中点为圆心、密集统计半径
  为像素圆，数圈内其他目标中点个数，取 1/(1+个数)，邻居越多分越低。

  - 魔方总分 = 权重距离 × 距离因子 + 权重密集 × 密集因子
  - 球总分 = 权重距离 × 距离因子 + 权重颜色 × 颜色分值 + 权重密集 × 密集因子

```
function 评分选靶(目标列表, 帧, 本轮品类) -> 排序列表:
    圆 = 抓取圈(帧尺寸)                          # (cx, cy, r)
    for 目标 in 目标列表:
        分 = 权重距离 × 距离因子(目标.中点, 圆)
        if 本轮品类 == 球:
            分 += 权重颜色 × 该颜色分值(主色(帧, 目标.ROI))
        分 += 权重密集 × 密集因子(目标, 目标列表, 密集半径)
        目标.score = 分
    按 score 从高到低排序（并列稳定，编号小在前）
    return 排序列表
```

### 3.3 技术实现要点（大概，后面按此实现或搬用）

- 评分做成纯函数：输入目标列表 + 帧，输出写回 score 的排序列表，
  不碰其他运行状态。
- 主色判定：六色 BGR 区间 + 形态学开闭去噪，取 ROI 内色块总面积最大
  的颜色（上一版 color_blob 思路）。
- 抓取圈换算与手动模式画圆公式一致（看到即可抓）。
- config 参数：魔方/球各自的三因子权重、plateau 比例、密集统计半径、
  六色球分值。
- 设计说明：不做"失败目标排除"——每次抓取（无论成败）都可能改变
  物体位置，评分每轮重算，自然反映新布局。
- 待确认：
  1. 密集因子的邻居算谁——同品类目标，还是跨品类（上一版球评分时
     数的是周边魔方）？
  2. 六色球分值初始表。
  3. 并列打破规则：编号小者优先是否够用。

## 阶段四：抓取执行（发指令 + 三舵机角度判定成败）

### 4.1 职责与出入参

- 职责：对阶段三选中的目标执行抓取——把目标 ROI 中点换算成现实中
  的位置发给下位机，并与执行机构交互，按**三个舵机的角度**判定是否
  抓取成功。
- 输入：阶段三选中的目标（ROI 中点像素坐标 + 品类）+ 执行机构回传
  ActuatorState。
- 输出（三态约定）：
  - `True` = 抓取成功 → 阶段五（人工起飞转场）
  - `False` = 抓取失败 → 跳回【阶段二】重新判定可抓
  - `None` = 无法判定（无回传 / 串口异常）
- 计数：本阶段不改变 N（抓取任务还没完成，成败都不 +1）。

### 4.2 流程分支（树状；伪代码待流程确认后补）

1. 取阶段三选中的目标 ROI 中点（像素坐标）。
2. 调 common 里的坐标映射方法：像素 → 现实中的位置。
3. 组协议帧经串口发给下位机执行抓取（X/Y/N/RX 语义待电控确认 §4.5-1）。
4. 等待机构动作：拉模式读回传 ActuatorState（只取最新一帧）。
5. 按三舵机角度判定抓取成功（判定要素见 4.3）。
6. 成功 → 计数装置记录（本轮选中目标 / 成功标记）→ 阶段五。
7. 失败 → 跳回【阶段二】重新判定可抓（N 不变，相当于重新选靶；
   同一轮内失败上限 3 次，见 §4.5-3）。
8. 全程受本阶段时间周期约束，超时走超时分支（处理方式待确认 §4.5-4）。

### 4.3 抓取成功判定：三舵机角度（沿用上一版 grab_check 思路，待重写）

这里只保留**判定要素**，组合逻辑与阈值后面按流程一步步重写：

- 伸缩舵机1：是否在伸缩运动范围内
- 伸缩舵机2：是否在伸缩运动范围内（两舵机共用一套范围）
- 伸缩舵机1/2：两舵机角度偏差 ≤ 容差（机构正常、无卡斜）
- 伸缩舵机1/2：是否处于静止保持位置范围（抓取成功/未抓取时机构都
  会停在保持位置）
- 抓取舵机：是否已离开静止角度范围（= 执行了夹取动作）

  现场标定。

- 回传读取：actuator 拉模式读最新一帧（五项一帧整体覆盖）。

- 阶段时间周期：等待回传 + 判定的总窗口 config 化，超时走超时分支。

  现场调试，调准后圈内抓取即准。
- 涉及模块：actuator（收发 + 状态）、common 坐标映射、flow（编排 + 计数）。

## 阶段五：起飞转场（抓取成功 → 直接起飞 → 重新降落判定）

### 5.1 职责与出入参

- 职责：阶段四判定抓取成功后，飞行器**直接起飞**；状态机切换为
  【飞行中】，随后走阶段一的降落判定（重新降落，预期在投放位置）。
- 输入：阶段四的抓取成功判定。
- 输出：
  - `True` = 已起飞并切入飞行中（流程跳回阶段一）
  - `None` = 起飞异常无法确认
- 计数：N 不变（本轮抓取任务还没走到投放）；计数装置写入
  **已抓物品标记 = 本轮品类**（供重新降落后的状态路由）。

### 5.2 流程分支（树状；伪代码待流程确认后补）

1. 阶段四抓取成功 → 状态机切换为【飞行中】。
2. **人工起飞**（飞机由人飞，已定）。
3. 确认起飞完成 → 飞行途中（脱落监视 API 场景一持续工作：掉落 →

4. 抵达投放区降落 → 跳回【阶段一】降落判定（落点由人工选择）。
5. 重新判稳通过后，按计数装置的**已抓物品标记**分流：已抓物品 →
   投放系列（阶段六）——这是降落判定之后的分流点，抓取轮与投放轮
   共用阶段一。
6. 长时间未起飞 → 提示人工。

### 5.3 技术实现要点（大概）

- 状态机切换：FlowCounter 当前状态 = 飞行中 + 已抓物品标记 = 本轮品类。

  变化 = 已起飞），或由人工确认，待定。
- 重新降落完全复用阶段一的判稳逻辑与 config 参数（同一套）。

## 阶段六：投放执行（容器可投判定 → 发指令投放；完成 = 动作完成 或 判定脱落）

### 6.1 职责与出入参

- 职责：抓着物品降落停稳后（投放态），用 YOLO 识别投放容器并判定
  是否可投；可投则**直接调 common 的串口方法发投放指令**。
- **投放完成定义（已定）**：投放动作执行完成 **或** 舵机角度变化判定
  物品脱落——两者都判定为本轮投放完成（掉了就掉了，不回炉重抓），
  N+1 进入下一轮，必须切换到下一个品类的抓取。
- 输入：当前帧（YOLO 识别）+ 本轮已抓品类（计数装置的已抓物品标记：
  魔方 → 找盆 / 球 → 找桶）。
- 输出：
  - `True` = 本轮投放完成（动作完成 或 判定脱落）
  - `None` = 识别不可用（无帧/相机断线），无法判定
  - 不可投不产生"失败输出"：提示人工重新飞 ⇒ 阶段一 → 再进阶段六
- 通过后的动作：N+1（品类随之切换）、已抓物品标记清空 → 提示人工
  飞回抓取区 ⇒ 阶段一判稳 → 阶段二开始下一轮。

### 6.2 可投判定标准（分容器，两条判据）

- **盆（投放魔方）**：YOLO 识别盆 ROI，与抓取圈的**重合面积 ≥ 阈值**
  （重合像素数）即判定可投——盆大、颜色均匀、首次投放为空，只要
  "有一定的面积在抓取范围内"就行（沿用上一版 judge_cube_droppable
  的判据）。
- **桶（投放球）**：YOLO 识别桶 ROI，**ROI 中点必须落在抓取范围内**
  才判定可投（沿用上一版 judge_ball_droppable 的判据——上一版曾
  标注"不可靠占位"，现在按此定稿，可靠性现场验证）。
- 防抖：连续 M 帧判定结论一致才执行（沿用识别防抖约定）。

### 6.3 流程分支（树状；伪代码待流程确认后补）

1. 计数装置给出已抓品类（魔方 → 盆 / 球 → 桶）。
2. 取当前帧 → YOLO 识别（盆/桶一次推理全出），只看对应容器。
3. 防抖：连续 M 帧结论一致才认定；不一致 → 回跳 2。
4. 按品类选判据：魔方 → 盆重合面积 ≥ 阈值；球 → 桶中点在抓取圈内。
5. **落地全程并行**：脱落监视 API 场景二——还未主动投放就掉落 →
   **视同投放完成**，直接跳第 9 步（见 §7.2）。
6. 不可投 → 防抖重试确认 → **提示人工重新飞**（切【飞行中】，N 不变、
   已抓物品标记保持）⇒ 跳回【阶段一】重新判降落 → 再进阶段六
   （"飞了还投不了"的循环次数上限见 §6.5-3）。
7. 可投 → 调 common 串口方法发投放指令（协议语义待电控确认 §6.5-1）。
8. **投放完成判定**（二选一即算完成）：
   a. 投放动作执行完成（指令发出、机构动作到位）；
   b. 脱落监视判定物品已脱落（舵机角度变化，见 §6.6）。
9. 任一成立 → 计数 N+1、已抓物品标记清空 → 提示人工飞回抓取区 ⇒
   阶段一判稳 → 阶段二（下一轮，品类随 N 切换）。

### 6.4 技术实现要点（大概）

- 盆/桶识别：与阶段二共用同一条 YOLO 推理链路（一次出四类），
  本阶段消费 pan / bucket 的识别结果。
- 重合面积判定：region 模块的"ROI 与抓取圈重合像素数"（对比板思路）。
- 中点判定：region 模块的"像素点是否在抓取圈内"。
- 指令发送：common/hardware/serial_protocol.py（与手动模式同协议同帧），
  单发 / 连发待电控确认。
- 参数全部 config 化：盆重合面积阈值 / 防抖帧数 M / 重试上限 /
  阶段时间周期。
- 设计决定：投放完成 = 动作完成 或 判定脱落（不做投放"成功/失败"
  判定，掉了视同完成）。
- 涉及模块：detection（识别）、region（两项判定）、actuator / common
  （发送）、flow（编排 + 计数）。

### 6.6 技术讨论：总线舵机怎么判定"物品脱落"（待研究定稿）

背景：投放完成的判定包含"脱落"分支，且三种掉落场景（**飞行中掉落 /
落地后掉落 / 重飞途中掉落**）的处理模式各不相同，因此脱落检测做成
**独立的时刻监视 API/接口**（监视抓取机构舵机角度状态），flow 按
当前场景调用对应的处理函数。本节只讨论"怎么知道脱落了"，各场景的
处理策略已定稿（见 §7.2 场景表）。

**思路 A：角度越界法（纯角度回读，无额外硬件）**

- 夹爪夹住物品时，夹取舵机停在"对应目标的夹取角度范围"内（魔方/
  球分开配置——物品尺寸不同，停住的角度不同）。
- 物品脱落后爪瓣失去阻力，舵机会继续向**空爪闭合位**闭合——角度
  越过目标夹取范围的边界并稳定在更小的角度。
- 判定：时刻监视夹取舵机角度，一旦**越过对应夹取范围的边界并稳定**
  → 判定脱落（"稳定"判定可复用阶段一连续 N 次稳定的思路）。
- 前提：空爪闭合位与夹球/夹魔方角度要有可分辨的差（待实测）。

**思路 B：负载/电流回读法（取决于总线舵机型号）**

- 总线舵机通常可回读负载（load）/电流/温度等状态。抓着物品时舵机
  保持扭矩、负载持续偏高；脱落瞬间负载骤降到空载水平。
- 判定：负载从"夹物负载带"跌出或突变超阈值 → 判定脱落。
- 优点：直接、灵敏；前提：舵机固件支持回读且数据可用（待电控确认）。

**建议**：A 为主、B 为辅——A 不依赖固件能力、一定可用；B 若可用则
响应更快更直接。接口形态：`脱落监视 API`（输入：回传数据流/轮询；
输出：脱落事件 + 场景上下文），三种掉落场景分别包装成独立处理函数。

待电控/实测确认：

1. 总线舵机型号与可回读量（角度肯定有；负载/电流/温度看型号）；
2. 空爪闭合角度 vs 夹球/夹魔方角度的区分度（思路 A 可行性）；
3. 回传频率能否支撑"时刻监视"（脱落发生到判定的延迟要求）；
4. ~~三种掉落场景各自的处理策略~~ **场景一/二已定稿（§7.2 场景表）；
   仅场景三（重飞途中掉落）待定义，倾向并入场景一**。

## 七、全局监视（贯穿各阶段，独立 API）

两个监视器与具体阶段解耦：任何读回传的时刻、任何"已抓物品"的
状态（飞行中 / 落地投放态 / 重飞途中）都在工作，处理后按场景跳转
（与流程图 SG7 对应）。

### 7.1 机构异常监视（G2）

- 监视对象：伸缩舵机1/2 + 抓取舵机的角度。
- 判定：角度**持续不在任何已知状态**——运动范围 / 目标夹取范围 /
  静止保持位（既不在正常运动、也没夹着东西、也不是静止待命）→
  判定机构异常（卡死 / 故障 / 松脱）。
- 处理：提示人工处理；恢复后的续跑点由人工决定（飞机在人手上）。
- 实现：与脱落监视同一套"时刻监视"框架，独立函数接口。
