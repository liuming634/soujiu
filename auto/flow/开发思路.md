# flow 开发思路（实现路线记录）

记录 flow 的两种写法对比与定稿路线（2026-10-17 口述拍板）。

## 一、两种写法对比

### 树状结构写法（第一步，先做）

- 形态：把各阶段做成**阶段函数**，阶段内部用 if 判断把分支嵌套出来
  （可抓/不可抓、成功/失败、重试、超时……），调用完一个阶段按分支
  结果走下一个阶段——阶段套阶段，整条流程是一棵调用树。
- 优点：合理、写出来最快、最直观；伪代码定稿各阶段的分支表/树状
  处理本来就是这个形状，照着写就行；业务逻辑先跑通。
- 特点/局限：本质是 if 叠加出来的**线性流程**，流程怎么走写死在
  调用关系里；代码量和分支数成正比。

### 状态监控调度模式（第二步，后改）

- 形态：**只做两个处理端循环**——状态监控读状态 → 分派给对应状态
  接口 → 接口执行完**修改状态** → 回到状态监控再调度。流程怎么走
  不写在调用关系里，而是由"状态位 + 各接口自己写的状态切换"驱动。
- 优点：**代码量最小、复用最高**；调度器极简，阶段逻辑对调度透明。
- 缺点：调度逻辑抽象、理解比较困难、写起来有点难——状态的归属、
  接口之间的衔接都要想清楚才能写对。

## 二、定稿路线：两步走

1. **第一步（现在）：直接写树状结构**。用 if 判断嵌套出分支，把
   "每个状态里该干什么、分支怎么走"先落实成能跑的代码。
2. **第二步（树跑通后）：改造成状态监控调度模式**。把树拆成状态
   接口交给状态监视线程调度——每个函数体几乎原样搬进对应接口，
   改动量很小，主要是把"调用关系"换成"状态驱动"。

顺序的理由：树状版先把业务分支落实成可跑代码，拆接口时内容不变、
只换外壳；反过来先写调度模式，分支没定型、调度逻辑又难，两头都悬。

## 三、现状与边界

- **已就位**（auto/flow/main.py 线程装配层，先行完成）：STM32 回传
  接收、IMU 落地判定监视、状态监视（flying → landed → 按已抓标记
  路由 grab/drop）、相机取帧；数据统一进 RuntimeData。第二步的
  "状态监控"就从这套线程长出来。
- **待写**：树状阶段函数（阶段一~六 + 全局监视挂点）。阶段逻辑
  按口述逐段实现——未口述的不自行实现、C 类未定项不预设默认值。
- **分支依据**：伪代码定稿各阶段（分支表/树状处理/待确认节）；
  写的时候发现走向与定稿对不上的，先问再写，走向有变时同步改
  伪代码。
- 参数全部进 auto/params.py（flow 段），阈值/上限/周期不写死。
