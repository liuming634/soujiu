## 一、任务与角色分工

CADC 模拟搜救任务：无人机在场地内识别并抓取魔方/球，飞到投放区投进
盆/桶。**飞行始终由人工操作**，本代码只自动化"抓取机构"这一段——
识别、判定、给下位机发指令、推进状态；"是否重新飞"由人工决定。

一轮任务的物理流程（人工飞 + 代码判）：

```
起飞 → 飞到抓取区降落 → 识别目标 → 抓取 → 起飞转场
     → 飞到投放区降落 → 识别容器 → 投放 → 飞回 → 下一轮（品类交替）
```

要完成的比赛任务（即自动链路要自动化的东西）：

1. **识别目标**：画面中的魔方（cube）和球（ball）。
2. **选目标**：在"抓取圈"（机构可达范围）内，按评分选先抓谁。
3. **抓取**：发串口指令让下位机执行，按舵机角度回传判定抓取是否成功。
4. **投放**：魔方投大盆（pan）、球投桶（bucket），投放前判定容器可投。
5. **循环 1→4**，直到魔方投满 15 个完赛。

## 二、实现模式：从阶段树到状态驱动（方案选型）

开发中对比/演进过三种写法（过程稿 git 历史可查）：

| 写法                                  | 形态                                                         | 结论                                                                 |
| ------------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------- |
| 阶段树状调用                          | 每个阶段一个函数，阶段内 if 嵌套分支，调用完按分支进下一阶段 | 第一步用它把业务分支跑通；本质是写死的线性流程，改一个场景要动调用链 |
| **轮询 + 状态驱动（定稿实现）** | 监视线程直改状态量，while 大循环只读分发                     | 代码量最小、复用最高；加一个异常场景 = 加一层 if，不动老代码         |
| 行为树（py_trees）                    | 状态量做黑板，六情况做动作叶子                               | **与状态驱动等价，写起来更方便**（见 §2.3，推荐参考者采用）   |

实际开发就是"两步走"：先按阶段树伪代码把各阶段的分支逻辑落实成
能跑的代码，再把阶段函数体原样搬进状态驱动的接口里——分支内容
不变、只把"调用关系"换成"状态驱动"。

### 2.1 状态驱动的两条核心纪律

1. **监视线程只管直改状态量**（写 `RuntimeData`），不通知、不分发——
   状态"是什么"和"拿到状态后干什么"彻底分离；
2. **接口处理只改状态与记账，不连着调下一步**——识别完不直接抓，
   发完指令不直接判成败；动作在**下一轮轮询**里由新状态驱动。

### 2.2 FreeRTOS 式轮询骨架（现实现）

```
┌─ 监视线程（生产者：持续监控 → 直改 RuntimeData 状态量）──────────┐
│  STM32 接收线程    机构回传 → actuator_state（0x02）/ imu_state（0x03）│
│  接收机判飞行线程  遥控器信号 → auto_flight_state（层1，flying/landed）│
│  机构监视线程      舵机角度采样入长队列 → auto_mech_state（层2三态）    │
│  YOLO任务判定线程  识别结果 → yolo_task（四任务类别）                  │
│  相机取帧线程      current_frame                                      │
└──────────────────────────────┬───────────────────────────────┘
                               │ 只读状态量
┌──────────────────────────────▼───────────────────────────────┐
│  while 大循环 _main_loop（消费者/调度，50ms 一轮）              │
│  第一层 if：飞行状况（flying / landed）                        │
│    └ 第二层 if：机构状况（idle / hold / process）              │
│       └ 第三层 if：任务记账（grab_sent/drop_sent）/ yolo_task  │
│  每个接口处理只改状态与记账 → 下一轮轮询走对应分支              │
└──────────────────────────────────────────────────────────────┘
```

### 2.3 行为树：等价且更方便的调度写法（推荐参考者采用）

状态驱动里的"两层状态量 + 记账"天然就是行为树的**黑板（blackboard）**，
六情况天然就是**动作叶子**——业务逻辑完全同构，行为树只是把"分发
优先级"从三层嵌套 if 搬进树形结构：

| 状态驱动（现实现）           | 行为树（等价写法）                         |
| ---------------------------- | ------------------------------------------ |
| RuntimeData 状态量与记账字段 | 黑板 blackboard                            |
| 大循环三层 if 的每个分支体   | 动作叶子节点（函数体原样搬）               |
| 层1/层2/层3 的嵌套表达优先级 | Selector 表达优先级、Sequence 表达层内顺序 |
| while 大循环轮询             | tick()                                     |

树形结构对照（叶子名 = 现 if 分支，逐段可搬）：

```
Root（Selector，自上而下优先级）
├─ 完赛检查      cube_done ≥ 15 → HALT（提示收尾，流程结束）
├─ 飞行分支      条件 flying → Selector(
│                  飞行中掉落处理，   # process + 有账未处理：翻转记账
│                  兜底补账，         # hold + 无账
│                  等待)              # idle / 其余：等落地
└─ 落地分支      条件 landed → Selector(
                   Sequence[条件 idle → Selector(抓取验证超时， 选靶发指令， 等待)],
                   Sequence[条件 hold → Selector(抓取成功收口， drop_sent 等待， 发投放指令， 等待)],
                   Sequence[条件 process → 投放完成记账])
```

为什么说更方便：

- **优先级写在树形结构里**，不用在嵌套 if 里靠代码位置表达"先判谁"，
  读树即读优先级；
- **加一个异常场景 = 挂一个高优先级叶子**，其他分支零改动——与状态
  驱动"加场景 = 加 if"同级，但结构可视、可独立测试；
- py_trees 纯 Python、树莓派可用，自带 tick 调度与行为树可视化（可导出
  dot 图），调试时直接看到当前走到哪个叶子；
- 监视线程骨架**原样复用**（生产者照旧写黑板），只把 `_main_loop` 换成
  tick 循环。

当前版未采用的原因：团队更熟悉单片机式写法、零第三方依赖。两者随时
可换，实现路径细节另见 [扩展功能技术路线.md §6](扩展功能技术路线.md)。

## 三、模块划分与总体架构

按职能分五个模块：

| 模块            | 职责                                                                              | 代码                                                |
| --------------- | --------------------------------------------------------------------------------- | --------------------------------------------------- |
| 起飞判定模块    | 判定飞行/落地（层1 flying/landed），三判定源并列                                  | `auto/landing/` + flow 接收机判飞线程             |
| 任务识别模块    | 识别结果直接定任务（抓魔方/抓球/投盆/投桶）                                       | `auto/detection/` + flow YOLO 判定线程            |
| 状态监视模块    | 时刻监控机构状况（idle/hold/process），判别"现在到底是什么状况"、给脱落检测供材料 | `auto/actuator/judge_grabber` + flow 机构监视线程 |
| flow 调度模块   | 总调度（FreeRTOS 式轮询）+ 决策处理（六情况分发、两条任务链、计数记账）           | `auto/flow/main.py`                               |
| common 工具复用 | 相机采集/串口协议/坐标映射/数据中心/config，作为调用 API                          | `common/`（见 §五）                              |

协作关系：flow 是唯一编排者——通过各模块的函数 API 把能力串起来
（detection 识别 → region 圈内过滤 → scoring 评分选靶 → common 坐标
映射 → actuator 收发；landing 提供判定源）。平级模块间不互相调用
（例外：scoring 复用 detection 色块工具与 region 圈换算，工具级）。
各模块对外 API 一览与 RuntimeData 数据约定见 [开发约束.md](开发约束.md)。

两层状态组合 = **2 × 3 = 六种情况**，覆盖任务全程：

| # | 层1    | 层2     | 物理含义               | 处理                              |
| - | ------ | ------- | ---------------------- | --------------------------------- |
| 1 | flying | idle    | 空爪飞行               | 无动作，等落地                    |
| 2 | flying | hold    | 抓着东西转场           | 兜底补账，等落地                  |
| 3 | flying | process | 飞行中掉落             | N+1 且奇偶映射翻转 → 提示重抓    |
| 4 | landed | idle    | 落地空爪               | YOLO 判定 → 抓取链路             |
| 5 | landed | hold    | 落地抓着东西           | 抓取收口 / YOLO 判定 → 投放链路  |
| 6 | landed | process | 落地松开（投放或掉落） | 记投放完成：N+1、计消耗、提示飞回 |

## 四、各模块实现路径

### 4.1 起飞判定模块（层1：flying / landed）

- **主判据 = 接收机**：飞行中人工持续操作 → 有信号；落地后人工基本
  不再操作 → 超时收不到信号即判落地。监视线程每 0.05s 判一次、直改
  `auto_flight_state`；数据源待电控接入（占位恒判落地，不影响其余
  链路调试），判定口径三选一（链路在线 / 通道值有变化 / 超时失联，
  见 `_receiver_signal_active` 注释）。
- **三个判定源并列设计**：接收机（主）/ IMU 落地冲击（`check_imu_impact`
  + `start_landing_monitor` 监视线程，结果写 `landing_imu_hit/_time`）/
    图像光流画面静止（`check_frame_still`，按帧喂图）。三者**同形态**——
    都是"监视线程持续判定、直改同一个状态量"，换主源 = 换线程，大循环
    一行不改。融合升级方向（冲击触发 + 多源短确认窗）见
    [扩展功能技术路线.md §1](扩展功能技术路线.md)。

### 4.2 任务识别模块（yolo_task）

- 思路：**YOLO 识别到什么 ≈ 该执行什么任务**。一个模型一次推理四类
  （魔方/球/盆/桶），判定线程 0.5s 一帧，识别结果直接映射成四种任务
  写 `yolo_task`：

| 识别结果 | 任务                   | 判定附加条件                                      |
| -------- | ---------------------- | ------------------------------------------------- |
| 盆       | `drop_cube` 投放魔方 | 盆 ROI 与抓取圈重合面积 ≥ 阈值（`overlap_ok`） |
| 桶       | `drop_ball` 投放球   | 桶 ROI 中点在抓取圈内（`point_in_range`）       |
| 魔方     | `grab_cube` 抓魔方   | ——                                              |
| 球       | `grab_ball` 抓球     | ——                                              |

- 约束：`yolo_task` **只在落地链路被消费**——所有执行动作都在落地后做
  （落地之后才需要识别）；"只在落地状态跑推理省性能"是留口选项。
- 识别防抖（连续 M 帧一致才算数）队列已建（`cube_queue/ball_queue`）、
  消费逻辑未接，路径见 [扩展功能技术路线.md §5](扩展功能技术路线.md)。

### 4.3 状态监视模块（层2：idle / hold / process）

抓取舵机只有三个状况，各对应一个角度范围（`judge_grabber` 分档，
范围参数在 `auto/params.py`，占位待现场标定）：

- `empty` 静止（空爪闭合位）｜`cube`/`ball` 抓取（夹着魔方/球）｜
  `None` 运动中（不在任何范围）。

监视线程的实现（收数、判定、改状态在同一个线程里）：

1. 每 0.05~0.1s 取一次分档结果，存进 `deque(maxlen=20)` 长队列
   （静态数据，靠数据量判定，不需要高频）；
2. **收到样本当场判**——抓取和放开的角度差别大，单样本即可判：
   - 夹着样本 → `hold`；
   - 空爪样本、但队列里之前有夹着记录 → `process`（脱落/松开当场
     捕捉，这就是长队列的意义）；
   - 一直空爪 → `idle`；运动中 `None` → 维持原状态。
3. 过程窗长 = 队列长：夹着的老样本滑出队列后自然退回 `idle`，
   不需要额外定时器；离开过程态时复位一次性事件标记 `process_handled`。

**脱落检测**（掉落的判定材料）用的就是这个监视：上刻夹着 + 这刻空爪
= 脱落。思路 A 角度越界法（现用单样本直判；完整版越界+稳定 N 次去抖）、
思路 B 负载/电流回读法，以及三个掉落场景的处理策略，见
[扩展功能技术路线.md §2](扩展功能技术路线.md)。已拍板口径：**落地后
掉落与投放完成记同一笔账**（掉了不回炉）；飞行中掉落走翻转记账（§4.4）。

### 4.4 flow 调度模块（大循环决策：两条任务链 + 计数规则）

**抓取链路**（落地 + 空爪）：`yolo_task` 是抓取任务才进链路 →
N 定奇偶得到本轮品类 → `detect` + `filter_grabbable` 圈内过滤
（ROI 中点在抓取圈内才算可抓，与手动模式画圆同源）→
`score_cubes / score_balls` 评分选靶（距离 + 颜色 + 密集加权，并列
编号小者优先；颜色仅球、密集按 C1 口径只算魔方邻域，评分树细节见
`auto/scoring/__init__.py` 注释）→ `PixelToPlaneMapper` 像素换算现实坐标 →
发抓取指令 → 记 `grab_sent` → 下一轮验证。验证超时算一次失败，
回识别重新选靶；连续 3 次失败提示人工重飞。

**抓取成功的收口判据**（设计要点）：`auto_grabbed` 只在收口时写、
投放完成时清——所以"**机构夹着东西但账上没记**"只可能是刚抓上，
写账即收口，不需要额外的中间记账。"等起飞还是找容器投放"也不用记账
区分：投放只认 `yolo_task`，没识别到可投容器就安静等（在抓取点等
人工起飞，在投放点等容器入圈）。

**投放链路**（落地 + 夹着）：`yolo_task` 是对应容器的投放任务 →
发投放指令 → 记 `drop_sent` → 等机构松开（层2 出现 `process`）。

例外任务：球要投进**对应颜色桶底**的桶——第一次投放完成后建一次
"颜色 ↔ 桶"映射，此后球按颜色选桶；属未实现的扩展任务，路径见
[扩展功能技术路线.md §4](扩展功能技术路线.md)。

**投放完成**（落地 + 过程）：N+1、对应品类消耗 +1、清标记清记账、
提示人工飞回。投放动作完成和落地掉落都算完成（掉了不回炉，见 §4.3
拍板口径）。

**计数与品类规则（掉落翻转机制）**：

- 抓取任务计数 **N 从 0 计：偶 → 魔方、奇 → 球**；球尽（6 个）后
  全抓魔方；魔方投满 15 个 → 任务完成。
- **飞行中掉落 = N+1 且奇偶映射翻转一次**（`parity_flip` 翻转位）。
  两个变化相互抵消，下一轮仍抓同一品类（重抓掉的那个）；正常的
  投放完成只 N+1 不翻转 → 品类正常切换。连续掉落连续这样处理，
  抓取顺序与后续逻辑完全不受影响——用一个翻转位代替"重抓同品类"
  特殊分支。
- 各阶段时间窗/上限全部参数化（`auto/params.py` flow 段），不写死。

**完赛收尾**：`cube_done ≥ 15` 提示"任务完成"，大循环退出；其余
监视线程由调用方 `stop_flow()` 统一回收（线程均为 daemon，进程退出
亦兜底）。

## 五、common 工具复用

口径：`common/` 是**工具 API 库**——手动链路用全套（GUI/交互/显示），
自动链路只取需要的四个工具；**有这些工具不代表非要使用**，链路按需取用。

| 工具            | 接口                                                                             | auto 链路用途                                    |
| --------------- | -------------------------------------------------------------------------------- | ------------------------------------------------ |
| common/hardware | `SerialComm`（18 字节协议 pack / send_data 单发 / send_data_repeat 连发）      | 抓取/投放指令发送（协议语义待电控定稿，见 §六） |
| common/hardware | `CameraManager`（采集 + 断线重连；`read_undistorted_frame` 采集+去畸变一步） | flow 相机取帧线程的帧源                          |
| common/logic    | `PixelToPlaneMapper`（单应性像素→平面，画面中心为原点 + 符号校正）            | 抓取目标像素坐标 → 现实坐标                     |
| common/logic    | 坐标编码口径（`_encode_coord`：×scale 1000 + offset 5000，截断 0~9999）       | 米→毫米协议值编码，auto 发指令直接复用          |
| common/core     | `RuntimeData`                                                                  | 全链路统一状态中心（两层状态 + 记账 + 接收队列） |
| common/core     | `config`（YAML 持久化 + `resolve_path`）                                     | 抓取圈比例等手动/自动共用参数、标定文件路径      |

auto 内部的工具级复用：scoring 复用 detection 色块工具判球主色、
复用 region 的抓取圈换算 `grab_circle`——除此之外平级模块不互调。

串口帧格式：发送帧 0x01（18 字节，布局见 [比赛说明.md](../比赛说明.md) §4）
与回传帧 0x02 机构状态 / 0x03 IMU（布局见 `auto/actuator/link.py` 头
注释）——自动与手动同帧同协议，收发共用一个串口。
