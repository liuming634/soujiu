# 自动抓取流程技术实现（方法与路径）

> 对应代码：`auto/flow/main.py`（总调度）、`common/core/runtime_data.py`（状态量）、
> `auto/params.py`（参数）。逻辑骨架另见 `auto/flow/伪代码.py`。
> 本文写给没跟过开发过程的人：讲清楚这套自动抓取流程是怎么想的、怎么搭的、
> 每个部分为什么这么做。

---

## 一、项目定位与分工

CADC 模拟搜救任务：无人机在场地内识别并抓取魔方/球，飞到投放区投进盆/桶。
**飞行始终由人工操作**，本代码只自动化"抓取机构"这一段——识别、判定、
给下位机发指令、推进状态机。项目已完赛，这套框架用于开源与技术沉淀，
追求链路完整、思路清晰，不做替代人工的完全鲁棒自动化。

一轮任务的物理流程（人工飞 + 代码判）：

```
起飞 → 飞到抓取区降落 → 识别目标 → 抓取 → 起飞转场
     → 飞到投放区降落 → 识别容器 → 投放 → 飞回 → 下一轮（品类交替）
```

## 二、方案选型：为什么是"轮询 + 状态驱动"

开发中对比过三种写法，最终定稿**FreeRTOS 式轮询调度**：

| 方案 | 形态 | 弃用原因 |
|------|------|----------|
| 阶段树状调用 | 每个阶段一个函数，函数里 if 嵌套分支，调用完按分支进下一阶段 | 本质是写死的线性流程，分支都要在调用关系里铺开；改一个场景要动调用链 |
| 行为树（py_trees） | 节点树 + tick | 概念换血成本高，团队更熟悉单片机式写法 |
| **轮询 + 状态驱动（定稿）** | 监视线程直改状态量，一个大循环轮询分发 | —— |

定稿方案的两条核心纪律：

1. **监视线程只管直改状态量**（写 `RuntimeData`），不通知、不分发——
   状态"是什么"和"拿到状态后干什么"彻底分离；
2. **接口处理只改状态与记账，不连着调下一步**——识别完不直接抓，
   发完指令不直接判成败；动作在**下一轮轮询**里由新状态驱动。
   好处：加一个异常场景就是加一层 if，不动老代码；每个分支读起来
   都是独立小段，不用追踪调用链。

## 三、总体架构

```
┌─ 监视线程（生产者：持续监控 → 直改 RuntimeData 状态量）──────────┐
│  STM32 接收线程    机构回传 → actuator_state（0x02）/ imu_state（0x03）│
│  接收机判飞行线程  遥控器信号 → auto_flight_state（层1，flying/landed）│
│  机构监视线程      舵机角度采样入长队列 → auto_mech_state（层2三态）    │
│  YOLO任务判定线程  识别结果 → yolo_task（四任务类别）                  │
│  相机取帧线程      current_frame                                      │
└──────────────────────────────┬───────────────────────────────┘
                               │ 只读状态量
┌──────────────────────────────▼───────────────────────────────┐
│  while 大循环 _main_loop（消费者/调度，50ms 一轮）              │
│  第一层 if：飞行状况（flying / landed）                        │
│    └ 第二层 if：机构状况（idle / hold / process）              │
│       └ 第三层 if：任务记账（grab_sent/drop_sent）/ yolo_task  │
│  每个接口处理只改状态与记账 → 下一轮轮询走对应分支              │
└──────────────────────────────────────────────────────────────┘
```

两层状态组合 = **2 × 3 = 六种情况**，覆盖任务全程：

| # | 层1 | 层2 | 物理含义 | 处理 |
|---|------|------|------|------|
| 1 | flying | idle | 空爪飞行 | 无动作，等落地 |
| 2 | flying | hold | 抓着东西转场 | 兜底补账，等落地 |
| 3 | flying | process | 飞行中掉落 | N+1 且奇偶映射翻转 → 提示重抓 |
| 4 | landed | idle | 落地空爪 | YOLO 判定 → 抓取链路 |
| 5 | landed | hold | 落地抓着东西 | 抓取收口 / YOLO 判定 → 投放链路 |
| 6 | landed | process | 落地松开（投放或掉落） | 记投放完成：N+1、计消耗、提示飞回 |

## 四、各部分实现路径

### 4.1 层1：飞行 / 落地判定（接收机主源）

- 判据：**接收机有没有收到遥控器信号**——飞行中人工持续操作 → 有信号；
  落地后人工基本不再操作 → 超时没信号 → 判落地。
- 实现形态：独立监视线程每 0.05s 判一次，**直改** `auto_flight_state`。
- 三个判定源**并列设计**（代码注释里写明对应处理方法）：接收机（主）、
  IMU 落地冲击（`check_imu_impact`，监视线程已有）、图像光流画面静止
  （`check_frame_still`）。三者同形态——都是"监视线程持续判定、直改
  同一个状态量"，换主源 = 换线程，大循环一行不改。
- 现状：接收机数据源待电控接入，占位恒判落地（不影响其余链路调试）。

### 4.2 层2：抓取机构监视（长队列判三态）

抓取舵机只有三个状况，各对应一个角度范围（`judge_grabber` 分档，
范围参数在 `auto/params.py`，占位待现场标定）：

- `empty` 静止（空爪闭合位）｜`cube`/`ball` 抓取（夹着魔方/球）｜
  `None` 运动中（不在任何范围）。

监视线程的实现（收数、判定、改状态在**同一个线程**里）：

1. 每 0.05~0.1s 取一次分档结果，存进 `deque(maxlen=20)` 长队列
   （静态数据，靠数据量判定，不需要高频）；
2. **收到样本当场判**——抓取和放开的角度差别大，单样本即可判：
   - 夹着样本 → `hold`；
   - 空爪样本、但队列里**之前有夹着记录** → `process`（脱落/松开
     当场捕捉，这就是长队列的意义）；
   - 一直空爪 → `idle`；运动中 `None` → 维持原状态。
3. 过程窗长 = 队列长：夹着的老样本滑出队列后自然退回 `idle`，
   不需要额外定时器；离开过程态时复位一次性事件标记 `process_handled`。

### 4.3 YOLO 任务判定线程：识别结果直接定任务

思路：**YOLO 识别到什么 ≈ 该执行什么任务**。0.5s 一次 `detect(frame)`
（一个模型一次推理四类），识别结果映射成四种任务写 `yolo_task`：

| 识别结果 | 任务 | 判定附加条件 |
|----------|------|--------------|
| 盆 | `drop_cube` 投放魔方 | 盆 ROI 与抓取圈重合面积 ≥ 阈值（`overlap_ok`） |
| 桶 | `drop_ball` 投放球 | 桶 ROI 中点在抓取圈内（`point_in_range`） |
| 魔方 | `grab_cube` 抓魔方 | —— |
| 球 | `grab_ball` 抓球 | —— |

约束：`yolo_task` **只在落地链路被消费**——飞行段不走 YOLO 判定，
所有执行动作都在落地后做（落地之后才需要识别，飞行中跑推理没有意义）。

### 4.4 大循环两条任务链

**抓取链路**（落地 + 空爪）：`yolo_task` 是抓取任务才进链路 →
N 定奇偶得到本轮品类 → `detect` + `filter_grabbable` 圈内过滤
（ROI 中点在抓取圈内才算可抓，与手动模式画圆同源）→
`score_cubes / score_balls` 评分选靶（距离 + 颜色 + 密集加权，
并列编号小者优先）→ `PixelToPlaneMapper` 像素换算现实坐标 →
发抓取指令 → 记 `grab_sent` → 下一轮验证。验证超时算一次失败，
回识别重新选靶；连续 3 次失败提示人工重飞。

**抓取成功的收口判据**（设计要点）：`auto_grabbed` 只在收口时写、
投放完成时清——所以"**机构夹着东西但账上没记**"只可能是刚抓上，
写账即收口，不需要额外的中间记账。"等起飞还是找容器投放"也不用记账
区分：投放只认 `yolo_task`，没识别到可投容器就安静等（在抓取点等
人工起飞，在投放点等容器入圈）。

**投放链路**（落地 + 夹着）：`yolo_task` 是对应容器的投放任务 →
发投放指令 → 记 `drop_sent` → 等机构松开（层2 出现 `process`）。

**投放完成**（落地 + 过程）：N+1、对应品类消耗 +1、清标记清记账、
提示人工飞回。投放动作完成和落地掉落都算完成（掉了不回炉）。

### 4.5 计数与品类规则（掉落翻转机制）

- 抓取任务计数 **N 从 0 计：偶 → 魔方、奇 → 球**；球尽（6 个）后
  全抓魔方；魔方投满 15 个 → 任务完成。
- **飞行中掉落 = N+1 且奇偶映射翻转一次**（`parity_flip` 翻转位）。
  两个变化相互抵消，下一轮仍抓同一品类（重抓掉的那个），而正常的
  投放完成只 N+1 不翻转 → 品类正常切换。连续掉落就连续这样处理，
  抓取顺序与后续逻辑完全不受影响——这是用一个翻转位代替
  "重抓同品类"特殊分支的做法。
- 各阶段时间窗/上限全部参数化（`auto/params.py` flow 段），不写死。

## 五、复用的既有接口（本流程零新建底层能力）

| 模块 | 接口 | 用途 |
|------|------|------|
| auto/detection | `detect(frame)` | 一次推理四类（YOLO 权重占位待训练） |
| auto/region | `filter_grabbable / overlap_ok / point_in_range` | 圈内过滤、盆/桶可投判定（对比板查色，与手动画圆同源） |
| auto/scoring | `score_cubes / score_balls` | 距离+颜色+密集加权评分选靶 |
| auto/actuator | `open_comm / start_receiving / judge_grabber` | 串口回传接收、舵机角度分档 |
| auto/landing | `check_imu_impact / check_frame_still / check_receiver_lost` | 层1 并列备选判定源 |
| common | `SerialComm.send_data`、`PixelToPlaneMapper`、`RuntimeData`、`config` | 指令发送（语义待电控）、像素→现实坐标、统一状态存储 |
