## 1. 落地判定：三源并列（已实现）与融合升级（未实现）

### 1.1 现状：接收机主源，同形态换源

三个判定源**并列设计**、接口全部就绪：接收机（主源）/ IMU 跳变
（`check_imu_impact` + `start_landing_monitor` 监视线程）/ 图像光流
（`check_frame_still`）。三者同形态——"监视线程持续判定、直改
`auto_flight_state`"，**换主源 = 换线程，大循环与字段零改动**。
接收机读数未接入前线程占位恒判落地（`_receiver_signal_active` 返回
False，不影响其余链路调试）。

### 1.2 融合升级：冲击触发 + 多源短确认窗（原定采用方向，可随时升级）

当前实现是"单源直改"，未实现的升级是原方案的**多源并联确认窗**结构：

- **触发（毫秒级）**：IMU 加速度尖峰——触地瞬间出现远超 1g 的冲击尖峰
  （持续几十毫秒），跳变很快，慢的是"确认它真的稳了"的观察窗——所以
  把跳变从"要等它过去"变成"主动检测它"作为触发事件。
- **短确认窗（触发后约 0.5s，多源并联）**：
  - IMU：加速度回到 1g 附近带宽 + 角速度 ≈ 0（冲击已衰减、机体静止）；
  - 图像：前后帧光流幅值落区间 → 画面几乎没动；
  - 接收机：超过超时时长收不到遥控器信号即佐证落地；另可取辅助通道做
    自动模式使能开关（失控保护触发时通道跳变恰好用于退出自动）。
- **确认策略**：各源条件满足的条数达到设定值即通过（条数/权重可参数
  化），不必全部满足——单源失效不卡流程。
- **实现落点**：`check_imu_impact / check_frame_still / check_receiver_lost`
  三个接口已在 `auto/landing`；确认窗（时长/IMU 静止带宽/需满足条件数）
  是 flow 侧组合逻辑，在 `_receiver_flight_loop` 的位置加确认计数即可，
  大循环不用改。

### 1.3 下位机数据判稳（机构侧佐证，未实现）

与 IMU 互为佐证：一个看机体、一个看机构——actuator 回传的电机/舵机
读数空中（震动 + 机构微调）持续抖动、降落后趋于静止，**连续若干采样
周期帧间变化量 ≤ 容差 → 判定已降落**。可扩展把伸缩/夹取舵机（应处于
待命保持位）一并纳入判稳。数据源就在 `actuator_queue`（时间戳已打在
数据对象里），判稳函数可直接照 `_mech_monitor_loop` 的监视线程形态写。
待实测：回传频率、空中抖动幅度 vs 落地静止的区分度；若有下位机自身
降落状态位则优先用（更直接）。

## 2. 掉落（脱落）检测：两思路 × 三个掉落场景

### 2.1 数据链原理（两思路共用，收侧已就绪）

舵机角度负载由 STM32 底层回读 → 角度随 0x02 状态帧经串口回传 →
actuator 接收线程入 RuntimeData（`actuator_queue` + `actuator_state`
最新镜像）→ 判定工具取最新角度做范围判定。**核心物理现象**：抓取时
下发的指令角必然小于夹住物品后的保持角（爪瓣被物品挡住，舵机停在
指令角上方的夹取范围里）；物品脱落后爪瓣失去阻力，舵机继续向指令角
闭合——实际角度从夹取范围直接回落到指令角（≈ 空爪闭合位）。

### 2.2 思路 A：角度越界法（现用，纯角度回读、无额外硬件）

- **现用简化版**：机构监视线程低频采样 `judge_grabber` 分档，收到
  样本当场判（抓取/放开角度差别大，单样本即可判出），"上刻夹着 +
  这刻空爪 = 脱落"，长队列捕捉转变、老样本滑出自然退回 idle。
- **完整版（未实现，需要更高置信度时升级）**：时刻监视夹取舵机角度，
  一旦**越过对应夹取范围的边界并稳定**若干采样周期 → 判脱落（"稳定"
  = 连续 N 次采样确认，防途中抖动误判）；当前简化版单样本直判，若
  飞行震动导致爪瓣向闭合位滑动会误触发，换完整版即可解决。
- **现成判定函数**（旧分支 grab_check 思路，要素 API 化）：

  | 要素函数（思路） | 判定 | 参数 |
  |------|------|------|
  | check_grab_engaged | 抓取舵机已离开静止范围（= 执行了夹取） | grab_idle_range_min/max |
  | check_grab_in_target_range | 抓取舵机落在魔方/球夹取范围（分开配） | grab_cube/ball_range_min/max |
  | check_stretch_in_range | 伸缩舵机1/2 均在伸缩运动范围（共用一套） | grab_stretch_range_min/max |
  | check_stretch_aligned | 两伸缩舵机偏差 ≤ 容差（机构无卡斜） | grab_stretch_deviation_tol |
  | check_stretch_in_hold | 伸缩机构处于静止保持位范围 | grab_stretch_hold_range_min/max |
  | is_grabber_idle | 抓取舵机在静止范围（调度用） | grab_idle_range_min/max |

  三舵机角度入口现成（`ActuatorState` 已带 stretch_servo_1/2 /
  grab_servo 字段），可整套回归做完整版判定。

### 2.3 思路 B：负载/电流回读法（取决于总线舵机型号）

总线舵机通常可回读负载（load）/电流/温度：抓着物品时舵机保持扭矩、
负载持续偏高，脱落瞬间负载骤降到空载水平；判定 = 负载从"夹物负载
带"跌出或突变超阈值。优点：直接、灵敏；前提：舵机固件支持回读且
数据可用（待电控确认）。**接口形态与思路 A 相同**——只换监视线程里
的判定函数，`_mech_monitor_loop` 骨架不动。

### 2.4 掉落场景与处理策略（flow 侧，航途中判定由思路 A/B 承担）

| 场景 | 时机 | 处理 | 计数/标记 |
|------|------|------|-----------|
| 一 飞行中掉落 | 抓取成功起飞后、转场途中 | ✅ 已实现：N+1 且奇偶映射翻转 → 重抓同品类 | 标记清空、品类消耗不变 |
| 二 落地后掉落 | 投放态、还未主动投放 | ✅ 已实现：视同投放完成，提示飞回 | N+1、品类切换 |
| 三 重飞途中掉落 | 不可投后人工重飞途中 | 未定义（倾向并入场景一，代码结构天然支持：掉落处理只认两层状态，不区分掉落发生在哪一轮） | — |

## 3. 抓取成功判定的完整版与机构健康监视（G2）

- **现用简化版**：抓取舵机角度范围直判（`judge_grabber`）+ 大循环
  收口判据（"夹着东西但账上没记 = 刚抓上"），不需要逐要素判定。
- **完整版（未实现）**：按 §2.2 六要素表组合——伸缩舵机判**机构
  健康**（不在运动范围 / 偏差超容差 / 不在保持位 → 机构可能卡死/故障/
  松脱），大部分时间机构正常，在正常的基础上才用抓取舵机判抓取；
  组合方向沿用旧版（已执行夹取动作 + 抓取舵机进入对应目标夹取范围
  + 伸缩机构回到保持位 → 抓取成功）。
- **G2 机构健康监视（未实现）**：与脱落监视同一套"时刻监视"框架
  （独立线程 + start/stop 函数 API，参考 `landing/monitor.py`），
  输入三舵机角度，判定持续异常 → 提示人工处理，恢复后的续跑点由
  人工决定（飞机在人手上）。
- **自优化预留（思考保留，暂不做）**：以横向/旋转电机的闭环读数为
  抓取机构实际位置，与坐标换算出的目标坐标做差值，可支撑后续自优化；
  当前精度靠现场调试。

## 4. 颜色 ↔ 桶映射（第一次投放后建一次，未实现）

- **规则**：球要投进**对应颜色桶底**的桶里；魔方投盆无此要求。
- **时机**：第一次投放（N=0 那轮）完成之后马上做一次；此后映射一直
  有效（桶不动），后续轮次不再重复识别。
- **方法**：YOLO 识别定位各桶 → 对桶底区域（桶 ROI 下部还是整桶 ROI
  待定）用 color_blob 六色工具做主色判定 → 按桶序把颜色标签放进
  **六元素列表**对应位置 → 得到"桶序 → 颜色"映射。
- **球的投放走向**：投放阶段"球颜色 → 列表 → 桶"选投放目标。
- **接线点**：flow 大循环"落地 + MECH_PROCESS 投放完成"节点加一次性
  子流程位（完成后置标记不再触发）；映射存放放 RuntimeData（建议加
  `bucket_color_map` 字段）；判色工具现成：`dominant_color(frame, bbox)`。

## 5. 识别防抖 M 帧（队列已建、消费逻辑未用）

识别有漏检/边缘抖动，单帧结论不算数：RuntimeData 已预置
`cube_queue / ball_queue`（每项 = 一帧推理的该品类目标列表），既有
约定是**连续 M 帧一致才算数**（流程：识别结果逐帧入队 → 对比最近
M 帧 → 取一致目标或按出现次数多数表决）。当前大循环抓取链路
直接用单帧 detect 结果评分，把"取帧 → 入队 → M 帧一致再交给评分"
加上即可；detection 模块保持纯函数，入队与表决记账由 flow 完成。

## 6. 调度形态备选：行为树 / 单线程顺序

主链路定为 **FreeRTOS 式轮询调度**（监视线程直改状态量 + while 大循环
三层 if 分发），选型对比与理由见 [自动抓取技术实现.md §二]。两个等价
方案作为备选路径：

- **行为树（py_trees，纯 Python、树莓派可用）**：两层状态量与
  `yolo_task / task_memo` 充当黑板（blackboard），六情况（2×3 组合）
  各做一个动作叶子节点，Selector 按优先级表达第一层分发、Sequence
  表达层内顺序（等落地 → 判任务 → 执行）；监视线程与大循环骨架可
  原样复用，建议单独开分支实现。
- **单线程顺序处理**：不要监视线程、主循环里顺次"收数据 → 判定 →
  处理"。结构最简单，但收数与推理堵在一条循环里实时性差——本框架
  不采用，列出供参照。

## 7. 电控待接入项（接口已留、只差数据源/协议语义）

1. **接收机读数线程**：协议待定；接到后负责刷新
   `RuntimeData.receiver_last_time`（`set_receiver_signal`），消费侧
   `_receiver_signal_active` 按三选一口径实现（a 链路在线 / b 通道值
   有变化 / c 超时失联口径）——口径详见该函数注释。
2. **抓取/投放指令协议语义**：X/Y/N/RX 发什么值代表"到这个坐标抓取" /
   "投放"、单发还是连发——定稿后填 `_send_grab_command /
   _send_drop_command`（组帧走 `SerialComm.send_data`，米→毫米换算参考
   InteractionManager；连发用 `send_data_repeat`，cancel_event 可中断）。
3. **总线舵机型号与可回读量**：角度肯定有；负载/电流/温度看型号——
   决定掉落检测思路 B 能否启用。
4. **0x02/0x03 回传频率与 IMU 量程换算**：决定各监视线程采样间隔与
   各阈值的定值（现全在 `auto/params.py` 占位，实测标定后填）。
5. **下位机自身降落状态位**：若有则优先作为层1最直接的信号源。
